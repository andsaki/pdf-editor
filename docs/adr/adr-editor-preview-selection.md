# ADR: レイアウトエディタとプレビュー表示方式の選定

## Context

### 意思決定の背景、及び目的

本アプリケーションでは、ユーザーが請求書レイアウトを編集し、変更をリアルタイムにプレビューできる機能が中核です。これを実現するための要件は以下です。

- レイアウトをWebアプリ上で正確にプレビュー表示できること
- テキスト、画像、テーブルなどをドラッグ&ドロップで配置・編集できること
- エディタとプレビューの見た目が一致すること（WYSIWYG）

これらを満たしつつ、開発コストと柔軟性を考慮したアーキテクチャ選定が必要。

**注記**: PDF出力方式の選定は別のADRで扱う。このADRではレイアウトエディタとプレビュー表示の実装方式のみを扱う。

## References

- [react-pdf](https://react-pdf.org/)
- [react-rnd](https://github.com/bokuweb/react-rnd)
- [pdf-lib](https://pdf-lib.js.org/)

## Considered Options

以下の3つの選択肢を検討した：

**注記**: エディタUIライブラリ（react-rnd）の選定は`adr-dnd-library-selection.md`で扱う。このADRではプレビュー表示方式のみを扱う。

- **Option A**: pdf-lib + react-pdf（ハイブリッド方式）
- **Option B**: DOM/HTML/CSS
- **Option C**: Canvas自前実装

## Comparison Table

| 比較項目                             | A: pdf-lib + react-pdf     | B: DOM/HTML/CSS          | C: Canvas自前実装         |
| ------------------------------------ | -------------------------- | ------------------------ | ------------------------- |
| **プレビュー表示**                   | React-PDFコンポーネント    | HTML/CSS                 | Canvas                    |
| **背景レンダリング**                 | pdf-lib（画像・図形描画）  | 不要                     | Canvas API                |
| **レイアウト記述**                   | pdf-lib API (`drawImage`等)| HTML/CSS                 | Canvas API (`drawText`等) |
| **WYSIWYG（エディタ⇔プレビュー）**  | △ 異なるレンダリング       | ◎ 同じHTML/CSS           | △ 実装次第                |
| **座標管理**                         | px ⇔ pt変換必要            | px単位統一               | px単位                    |
| **柔軟性**                           | △ pdf-lib制約あり          | ◎ CSS全機能利用可        | ◎ 完全制御可能            |
| **学習コスト**                       | 高（2つのAPI）             | 低（HTML/CSS）           | 非常に高（Canvas API）    |
| **開発工数**                         | 高（3-4ヶ月）              | 低（1-2ヶ月）            | 非常に高（6ヶ月）         |
| **メンテナンス性**                   | △ 約650行の座標変換ロジック| ◎ 非常に良好             | △ 自前実装多              |

## Option A: pdf-lib + react-pdf（現状のmainブランチ）

### アーキテクチャ

```
InvoiceData（レイアウトデータ、px単位）
  ↓ px → pt変換
pdf-lib（画像・図形をPDFバイナリに描画）
  ↓ PDFバイナリ生成
react-pdf（PDFプレビュー表示）
  ↓ 上にエディタUI（react-rnd）を重ねる
```

**実装概要**:
1. pdf-libで画像・図形をPDFバイナリに描画
2. react-pdfでそのバイナリをプレビュー表示
3. エディタUI（react-rnd）を上に重ねて編集機能を提供

**座標変換の課題**:
- ブラウザDOMとPDF座標系で異なる単位系（ピクセル vs ポイント）を使用
- 原点位置の違い（左上 vs 左下）により垂直座標の変換が複雑
- DPI（解像度）の違いによる換算が必要

### 👍 Pros

- **クライアント完結**: サーバー不要でPDFプレビュー可能
- **高速レンダリング**: ブラウザ内で即座にプレビュー更新
- **PDFベースのプレビュー**: 画像・図形を正確にPDF形式で表示

### 👎 Cons

- **学習コスト高い**: pdf-lib、react-pdfの2つのAPIを習得必要
- **座標変換の複雑さ**: ブラウザDOM（ピクセル単位、左上原点）とPDF座標系（ポイント単位、左下原点）で異なる座標系を使用するため、相互変換ロジックが複雑化し保守コストが高い
- **WYSIWYG困難**: プレビュー（React-PDF独自レンダリング）と最終PDF出力で微妙な差異が発生
- **日本語フォント対応**: PDFライブラリでテキストを描画する場合、日本語フォントの手動埋め込みが必要で実装が複雑

## Option B: DOM/HTML/CSS（PR #1で移行中）

### アーキテクチャ

```
InvoiceData（レイアウトデータ、px単位）
  ↓ px → mm変換（htmlGenerator）
HTML/CSS（プレビュー表示）
  ↑ 同じChromiumエンジン
Puppeteer（PDF出力）※サーバー側
```

**実装概要**:
1. レイアウトデータ（px単位）からHTMLを生成（mm単位に変換）
2. ブラウザでHTML/CSSプレビューを表示
3. PDF出力時はPuppeteerが同じHTMLをレンダリング

**座標管理の利点**:
- ブラウザDOMとプレビューで同じ単位系を使用
- Puppeteerが同じレンダリングエンジンを使用するため、プレビューとPDF出力が完全一致

### 👍 Pros

- **完全WYSIWYG**: プレビューとPDF出力が同じブラウザレンダリングエンジン（Chromium）を使用
- **開発生産性が高い**: HTML + CSSの知識だけで実装可能、特別なAPI学習不要
- **座標管理がシンプル**: px単位で統一可能、複雑な座標変換ロジック不要
- **デバッグ容易**: ブラウザのDevToolsで直接検証可能
- **高い柔軟性**: CSS Grid、Flexbox等のモダンなレイアウト技術が利用可能
- **コード削減**: 座標変換ロジックを大幅に削減可能

### 👎 Cons

- **編集領域とプレビューのスタイル統一が必要**:
  - 編集領域で配置する要素と、プレビューのHTML要素で同じスタイル定義を維持する必要
  - 対策: 統一的なHTML生成ロジックを使用

## Option C: Canvas自前実装

### 👍 Pros

- **完全制御可能**: ピクセル単位での描画や座標制御が可能
- **軽量構成**: 依存関係が少なく、ブラウザのみで完結

### 👎 Cons

- **実装工数が非常に高い**: テキスト折り返し、イベント管理、表描画などすべて自前実装
- **WYSIWYG困難**: ブラウザのテキストレンダリングとCanvas APIのレンダリングエンジンが異なる
  - フォント、行間、文字間隔の挙動が異なる
  - テキスト折り返しを手動実装する必要がある
- **保守性が低い**: 複雑な描画ロジックが増えるため変更に弱い
- **アクセシビリティ**: Canvas内のテキストは選択・コピーできない

## Discussion

### 編集領域とプレビューの座標同期

どの選択肢でも、編集領域とプレビュー表示の座標同期が課題となる。

**Option A（pdf-lib + react-pdf）の場合**:
- ブラウザDOMとPDF座標系で異なる座標系を使用
- DPI変換、単位変換、原点変換が必要

**Option B（DOM/HTML/CSS）の場合**:
- 編集領域とプレビューで同じ座標系を使用
- 座標変換が最小限

**Option C（Canvas）の場合**:
- 座標変換は不要だが、描画ロジック全て自前実装が必要

### ブラウザ互換性

**Option A（pdf-lib + react-pdf）の場合**:
- `react-pdf`の依存ライブラリ`pdfjs-dist`により、Safari 13以前で`FinalizationRegistry`未対応問題が発生
- Safari 13は2019年リリースで、現行Safari 18から見ても古いため影響は限定的
- 参考: [Safari 13 Release Notes](https://developer.apple.com/documentation/safari-release-notes/safari-13-release-notes)

**Option B, C**:
- 標準的なブラウザAPI使用のため、モダンブラウザ全般で安定動作

## Decision

**当初はOption A（pdf-lib + react-pdf）を採用していたが、Option B（DOM/HTML/CSS）へ移行することを決定**

### 移行の理由

1. **開発生産性**: HTML/CSSの知識だけで実装可能、学習コストが低い
2. **WYSIWYG**: エディタとプレビューで同じレンダリングエンジンを使用し、見た目が完全一致
3. **座標管理**: px単位で統一でき、座標変換が不要（約650行削減）
4. **保守性**: 標準的なWeb技術のため、メンテナンスが容易
5. **拡張性**: CSS Grid、Flexboxなどモダンな技術を活用可能

### 移行による成果

| カテゴリ     | 項目         | 移行前 (Option A)                             | 移行後 (Option B)       | 効果          |
| ------------ | ------------ | --------------------------------------------- | ----------------------- | ------------- |
| **コード量** | 総行数       | -                                             | 大幅に削減              | ✅ 削減       |
|              | 依存関係     | `@react-pdf/renderer`, `pdf-lib`              | なし（標準HTML/CSS）    | -2パッケージ  |
|              | APIの数      | 2つ (pdf-lib, react-pdf)                      | なし（標準Web技術）     | -2 API        |
| **品質**     | WYSIWYG      | プレビューと最終PDF出力でずれあり             | 完全一致                | ✅ 向上       |
|              | 座標系       | 2つの座標系と変換ロジック                     | 単一座標系 (px)         | ✅ 簡素化     |
| **保守性**   | 学習コスト   | 2つのライブラリAPI習得必要                    | HTML/CSS (標準Web技術)  | ✅ 低減       |
|              | バグリスク   | 座標変換エラーの温床                          | 座標変換ロジック不要    | ✅ 削減       |
| **開発効率** | デバッグ     | PDF出力して確認                               | ブラウザDevToolsで即確認| ✅ 向上       |

## Consequences

### ポジティブな影響

- **開発速度の向上**: HTML/CSSの知識だけで実装可能
- **デバッグの容易性**: ブラウザのDevToolsで直接検証可能
- **座標変換エラーの撲滅**: px単位統一により、座標ずれの問題が解消
- **拡張性**: CSS Grid、Flexboxなどモダンなレイアウト技術を活用可能

### ネガティブな影響・トレードオフ

- **スタイル統一の注意が必要**: エディタUIとプレビューで同じスタイル定義を維持する必要
  - 対策: `htmlGenerator`で統一的なHTML生成を行う
  - 対策: エディタとプレビューで同じCSSクラス/スタイルを使用

### 技術面接での想定質問と回答

#### Q1: なぜ最初にOption Aを選んだのか？

**A**: クライアント完結で高速なPDFプレビューを実現するため。当初は座標変換の複雑さを過小評価していた。

#### Q2: Option Aの最大の問題点は？

**A**: ブラウザDOMとPDF座標系で異なる座標系（DPI、単位、原点）を使用するため、複雑な座標変換ロジックが必要だった。これが保守性を著しく低下させた。

#### Q3: Option Bへの移行で失うものは？

**A**: クライアント完結の高速プレビュー。ただし、プレビュー自体はHTML/CSSで即座に表示でき、PDF出力のみサーバー側で実行するため、UX上の問題は小さい。

#### Q4: なぜOption C（Canvas）を選ばなかったのか？

**A**: テキスト折り返し、フォントレンダリング、イベント管理などすべて自前実装が必要で、開発工数が6ヶ月以上と見積もられたため。また、ブラウザのテキストレンダリングとCanvas APIのレンダリングエンジンが異なるため、WYSIWYGの実現が困難。

#### Q5: ドラッグ&ドロップライブラリは？

**A**: react-rndを使用。ドラッグ&ドロップライブラリの選定は`adr-dnd-library-selection.md`で扱っている。このADRはプレビュー表示方式のみに焦点を当てている。

### 今後の展望

- レスポンシブ対応やダークモード対応も標準的なWeb技術で実装可能
- プレビュー画面の拡張（ズーム、ページ切り替え等）もHTML/CSSベースで容易に実装可能
