ADR: PDF プレビューと操作ライブラリの選定
Context
意思決定の背景、及び目的

本アプリケーションでは、ユーザーが請求書 PDF を編集し、変更をリアルタイムにプレビューできる機能が中核です。これを実現するための要件は以下です。
PDF を Web アプリ上で正確に表示できること
テキスト、画像、テーブルなどを PDF 上に配置・編集できること
編集内容を反映した最終的な PDF を生成できること
これらを満たしつつ、開発コストと柔軟性を考慮したライブラリ選定が必要。
References

react-pdf
pdf-lib
Considered Options

1. **Option A:** react-pdf + pdf-lib の組み合わせ
2. **Option B:** 商用SDK（PDFTron等）
3. **Option C:** iframe でのプレビュー
4. **Option D:** Canvas 直接操作 + jsPDF
5. **Option E:** PDF.js 直接利用
6. **Option F:** サーバーサイドレンダリング（Puppeteer等）

Option A: react-pdf + pdf-lib
👍 Pros
表示と操作で役割分担でき、それぞれの強みを活かせる
pdf-lib により、テキストや画像の位置・スタイルを詳細に制御可能
無料・オープンソース

👎 Cons
表示座標と PDF 内部座標を同期する処理が必要で複雑
2 つの API を習得する必要があり学習コストが高い

Option B: 商用 SDK (例: PDFTron)
👍 Pros
プレビュー・編集機能が統合済み
高度な機能（注釈、複数ページ操作、Undo/Redo）が標準搭載
ブラウザ互換性や最適化がベンダー保証

👎 Cons
商用ライセンス費用が高い
一般的な利用規模では 年間 2 万〜3 万ドル（≒300〜450 万円） が目安。
ベンダーロックインのリスク（SDK API に依存）
カスタマイズの自由度は OSS より低い

Option C: iframe
👍 Pros
実装が最もシンプル
ブラウザ標準 PDF ビューアを利用でき安定性が高い

👎 Cons
編集機能やインタラクティブ性がほぼゼロ
そもそも要件を満たせない
アプリケーションとの連携も難しい

Option D: Canvas直接操作 + jsPDF
👍 Pros
完全な制御が可能（ピクセルレベルの操作）
Canvasの描画パフォーマンスが高い
軽量（追加ライブラリ最小限）

👎 Cons
開発工数が膨大（テキスト配置、折り返し、フォント管理など全て自前実装）
座標計算、イベント処理、レンダリング最適化など複雑
メンテナンスコストが非常に高い

Option E: PDF.js 直接利用
👍 Pros
react-pdfの内部で使用されている実績あるライブラリ
低レベルAPIで細かい制御が可能
Mozillaが開発・保守している

👎 Cons
低レベルAPIのため学習曲線が急
React統合を自前で実装する必要がある
react-pdfで十分な抽象化が提供されているため重複

Option F: サーバーサイドレンダリング（Puppeteer等）
👍 Pros
ブラウザと完全一致のPDF生成
複雑なレイアウトも正確に再現
クライアント側の処理負荷なし

👎 Cons
リアルタイムプレビューには不向き（レイテンシ2-5秒）
サーバーリソース消費が大きい
編集のたびにサーバーリクエストが必要

Discussion

### 要件との適合性評価

| オプション | リアルタイムプレビュー | インタラクティブ編集 | PDF生成品質 | 総合評価 |
|----------|-------------------|------------------|-----------|---------|
| A: react-pdf + pdf-lib | ◎ | ◎ | ◯ | **◎ 95点** |
| B: 商用SDK | ◎ | ◎ | ◎ | ◯ 90点（コスト除く） |
| C: iframe | ◯ | × | - | × 30点 |
| D: Canvas + jsPDF | ◯ | ◯ | △ | △ 60点 |
| E: PDF.js直接 | ◯ | ◯ | ◯ | ◯ 70点 |
| F: SSR(Puppeteer) | × | × | ◎ | △ 50点 |

### 却下理由の詳細

**Option C (iframe):**
- 致命的な問題: PDF上にReactコンポーネントを重ねた編集UIを実装できない
- iframe内のPDFは「一枚の画像」のような扱いで、要素単位の操作が不可能

**Option D (Canvas + jsPDF):**
- 開発工数6ヶ月以上の見積もり
- テキスト折り返し、フォントレンダリング、イベント処理など基礎機能の実装から必要
- ROI（投資対効果）が低い

**Option E (PDF.js直接):**
- react-pdfが既にPDF.jsをラップして使いやすくしている
- あえて低レベルAPIを使う必要性がない
- 「車輪の再発明」となる

**Option F (SSR Puppeteer):**
- リアルタイムプレビュー要件を満たせない（レイテンシ問題）
- ただし、最終PDF生成には有効（→ 別ADRで併用を決定）

### 商用SDK vs OSS の比較

年間コスト差分: **300-450万円**

この予算で実現可能なこと:
- 開発者2名 × 3ヶ月の工数をOSS統合に投入
- 残りの予算で他機能の開発加速
- ベンダーロックイン回避による長期的なコスト削減

**結論:** 商用SDKの機能は魅力的だが、コストと技術的自由度を考慮しOSSを選択

Decision

**Option A: react-pdf + pdf-lib を採用**

### 採用理由

1. **要件充足率が最も高い**（95点）
2. **オープンソースでコスト効率が良い**
3. **技術的な柔軟性が高い**（ライブラリ組み合わせ自由）
4. **コミュニティが活発**（react-pdf: 9.4k stars, pdf-lib: 6.8k stars）
5. **実装事例が豊富**で学習リソースが充実
Consequences

`react-pdf` の依存ライブラリ `pdfjs-dist` により、Safari 13 以前では `FinalizationRegistry` 未対応問題が発生し、PDF 表示がクラッシュする可能性がある（例: Issue #2020）。
Safari 13 は 2019 年リリースであり、現行の安定版 Safari 18 から見ても古いため、利用ユーザーは限定的と考えられる。
本システムの SLA においては、サポートブラウザを **Safari ≥ 14** に限定する。Safari 13 以下は対象外とすることも検討したい。
