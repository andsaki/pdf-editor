PDF 操作のライブラリの選定
Context
意思決定の背景、及び目的

本アプリケーションでは、ユーザーが請求書 PDF を編集し、変更をリアルタイムにプレビューできる機能が中核です。これを実現するための要件は以下です。
PDF を Web アプリ上で正確に表示できること
テキスト、画像、テーブルなどを PDF 上に配置・編集できること
編集内容を反映した最終的な PDF を生成できること
これらを満たしつつ、開発コストと柔軟性を考慮したライブラリ選定が必要。
References

react-pdf
pdf-lib
Considered Options

1. **Option A:** react-pdf + pdf-lib の組み合わせ
2. **Option B:** 商用 SDK（PDFTron 等）
3. **Option C:** iframe でのプレビュー
4. **Option D:** Canvas 直接操作 + jsPDF
5. **Option E:** PDF.js 直接利用
6. **Option F:** サーバーサイドレンダリング（Puppeteer 等）
7. **Option G:** HTML/DOM ベースのエディタ + Puppeteer

Option A: react-pdf + pdf-lib
👍 Pros
表示と操作で役割分担でき、それぞれの強みを活かせる
pdf-lib により、テキストや画像の位置・スタイルを詳細に制御可能
無料・オープンソース

👎 Cons
表示座標と PDF 内部座標を同期する処理が必要で複雑
2 つの API を習得する必要があり学習コストが高い

Option B: 商用 SDK (例: PDFTron)
👍 Pros
プレビュー・編集機能が統合済み
高度な機能（注釈、複数ページ操作、Undo/Redo）が標準搭載
ブラウザ互換性や最適化がベンダー保証

👎 Cons
商用ライセンス費用が高い
一般的な利用規模では 年間 2 万〜3 万ドル（≒300〜450 万円） が目安。
ベンダーロックインのリスク（SDK API に依存）
カスタマイズの自由度は OSS より低い

Option C: iframe
👍 Pros
実装が最もシンプル
ブラウザ標準 PDF ビューアを利用でき安定性が高い

👎 Cons
編集機能やインタラクティブ性がほぼゼロ
そもそも要件を満たせない
アプリケーションとの連携も難しい

Option D: Canvas 直接操作 + jsPDF
👍 Pros
完全な制御が可能（ピクセルレベルの操作）
Canvas の描画パフォーマンスが高い
軽量（追加ライブラリ最小限）

👎 Cons
開発工数が膨大（テキスト配置、折り返し、フォント管理など全て自前実装）
座標計算、イベント処理、レンダリング最適化など複雑
メンテナンスコストが非常に高い

Option E: PDF.js 直接利用
👍 Pros
react-pdf の内部で使用されている実績あるライブラリ
低レベル API で細かい制御が可能
Mozilla が開発・保守している

👎 Cons
低レベル API のため学習曲線が急
React 統合を自前で実装する必要がある
react-pdf で十分な抽象化が提供されているため重複

Option F: サーバーサイドレンダリング（Puppeteer 等）
👍 Pros
ブラウザと完全一致の PDF 生成
複雑なレイアウトも正確に再現
クライアント側の処理負荷なし

👎 Cons
リアルタイムプレビューには不向き（レイテンシ 2-5 秒）
サーバーリソース消費が大きい
編集のたびにサーバーリクエストが必要

Option G: HTML/DOM ベースのエディタ + Puppeteer
👍 Pros
通常の Web 開発技術（HTML/CSS/React）で直感的に実装可能
DOM 要素を直接操作できるため、インタラクティブ性が非常に高い
ブラウザの標準機能（contentEditable、Drag & Drop など）を活用可能
Puppeteer で HTML → PDF 変換により、WYSIWYG が完全保証される
学習コストが低く、既存の Web 開発スキルをそのまま活用
フォント、レイアウト、スタイリングが CSS で完結し柔軟性が高い

👎 Cons
PDF 座標系との変換が不要な代わりに、印刷用 CSS の調整が必要
Puppeteer への依存が強く、サーバー側の PDF 生成が必須
ブラウザのレンダリング差異（特に印刷プレビュー）に注意が必要
既存の PDF を読み込んで編集する場合、PDF → HTML 変換が複雑

Discussion

### 要件との適合性評価

| オプション             | リアルタイムプレビュー | インタラクティブ編集 | PDF 生成品質 | 総合評価              |
| ---------------------- | ---------------------- | -------------------- | ------------ | --------------------- |
| A: react-pdf + pdf-lib | ◎                      | ◎                    | ◯            | **◎ 95 点**           |
| B: 商用 SDK            | ◎                      | ◎                    | ◎            | ◯ 90 点（コスト除く） |
| C: iframe              | ◯                      | ×                    | -            | × 30 点               |
| D: Canvas + jsPDF      | ◯                      | ◯                    | △            | △ 60 点               |
| E: PDF.js 直接         | ◯                      | ◯                    | ◯            | ◯ 70 点               |
| F: SSR(Puppeteer)      | ×                      | ×                    | ◎            | △ 50 点               |
| G: DOM + Puppeteer     | ◎                      | ◎                    | ◎            | **◎ 98 点**           |

### 却下理由の詳細

**Option C (iframe):**

- 致命的な問題: PDF 上に React コンポーネントを重ねた編集 UI を実装できない
- iframe 内の PDF は「一枚の画像」のような扱いで、要素単位の操作が不可能

**Option D (Canvas + jsPDF):**

- 開発工数 6 ヶ月以上の見積もり
- テキスト折り返し、フォントレンダリング、イベント処理など基礎機能の実装から必要
- ROI（投資対効果）が低い

**Option E (PDF.js 直接):**

- react-pdf が既に PDF.js をラップして使いやすくしている
- あえて低レベル API を使う必要性がない
- 「車輪の再発明」となる

**Option F (SSR Puppeteer):**

- リアルタイムプレビュー要件を満たせない（レイテンシ問題）
- ただし、最終 PDF 生成には有効（→ 別 ADR で併用を決定）

**Option G (DOM + Puppeteer) の採用可能性:**

- **技術的には最も優れた選択肢**（総合評価 98 点）
  - リアルタイムプレビューが即座（DOM レンダリング）
  - インタラクティブ性が最高（ブラウザ標準機能活用）
  - PDF 生成品質が完璧（Puppeteer による HTML → PDF 変換）
  - 学習コストが低い（既存 Web 開発スキル活用）
  - 開発工数が短い（1-2 ヶ月）

- **本プロジェクトで不採用とした理由:**
  - **既存 PDF の編集が要件に含まれる可能性**がある
  - PDF → HTML 変換は技術的に困難（レイアウト情報の損失、フォント問題など）
  - react-pdf + pdf-lib の組み合わせであれば、PDF の読み込み・編集が可能
  - 将来的な要件変更に対する柔軟性を重視

- **推奨される利用ケース:**
  - **新規作成のみ**の請求書エディタであれば、Option G が最適
  - テンプレートベースの文書生成システム
  - HTML メール → PDF 変換システム

| 比較項目                     | Option A                                        | Option G                                          | 優位性 |
| ---------------------------- | ----------------------------------------------- | ------------------------------------------------- | ------ |
| **開発難易度**               | 高（Canvas 座標系と PDF 座標系の変換が必要）   | 低（通常の HTML/CSS/React 開発と同じ）            | **G**  |
| **学習コスト**               | 高（react-pdf, pdf-lib の 2 つの API を習得）  | 低（既存の Web 開発スキルをそのまま活用）         | **G**  |
| **開発工数**                 | 2-3 ヶ月                                        | 1-2 ヶ月                                          | **G**  |
| **リアルタイムプレビュー**   | Canvas レンダリング（高速）                     | DOM レンダリング（即座）                          | **G**  |
| **インタラクティブ性**       | Canvas 上でイベント処理を自前実装              | ブラウザ標準機能（contentEditable, D&D など）活用 | **G**  |
| **PDF 生成品質**             | 中程度（座標ズレの可能性あり）                  | 高品質（Puppeteer による完全 WYSIWYG）            | **G**  |
| **既存 PDF の読み込み・編集** | ◎ 可能（pdf-lib で直接操作）                   | × 困難（PDF → HTML 変換が複雑）                   | **A**  |
| **柔軟性・拡張性**           | PDF の詳細操作が可能（注釈、署名、暗号化など） | HTML/CSS の範囲内に限定                           | **A**  |
| **ブラウザ互換性**           | Safari 14 以上が必要（FinalizationRegistry）   | モダンブラウザ全般で安定                          | **G**  |

**結論:**
- **新規作成のみ**の要件であれば、Option G が全ての面で優れている
- **既存 PDF の編集**が要件に含まれる場合は、Option A 一択
- 本プロジェクトでは将来的な拡張性を考慮し、**Option A を採用**

### 商用 SDK vs OSS の比較

年間コスト差分: **300-450 万円**

この予算で実現可能なこと:

- 開発者 2 名 × 3 ヶ月の工数を OSS 統合に投入
- 残りの予算で他機能の開発加速
- ベンダーロックイン回避による長期的なコスト削減

**結論:** 商用 SDK の機能は魅力的だが、コストと技術的自由度を考慮し OSS を選択

Decision

**Option A: react-pdf + pdf-lib を採用**

### 採用理由

1. **要件充足率が最も高い**（95 点）
2. **オープンソースでコスト効率が良い**
3. **技術的な柔軟性が高い**（ライブラリ組み合わせ自由）
4. **コミュニティが活発**（react-pdf: 9.4k stars, pdf-lib: 6.8k stars）
5. **実装事例が豊富**で学習リソースが充実
   Consequences

`react-pdf` の依存ライブラリ `pdfjs-dist` により、Safari 13 以前では `FinalizationRegistry` 未対応問題が発生し、PDF 表示がクラッシュする可能性がある（例: Issue #2020）。
Safari 13 は 2019 年リリースであり、現行の安定版 Safari 18 から見ても古いため、利用ユーザーは限定的と考えられる。
本システムの SLA においては、サポートブラウザを **Safari ≥ 14** に限定する。Safari 13 以下は対象外とすることも検討したい。
