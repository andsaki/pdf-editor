ADR: PDF 操作のライブラリの選定
Context
意思決定の背景、及び目的

本アプリケーションでは、ユーザーが請求書 PDF を編集し、変更をリアルタイムにプレビューできる機能が中核です。これを実現するための要件は以下です。
PDF を Web アプリ上で正確に表示できること
テキスト、画像、テーブルなどを PDF 上に配置・編集できること
編集内容を反映した最終的な PDF を生成できること
これらを満たしつつ、開発コストと柔軟性を考慮したライブラリ選定が必要。

Option A: react-pdf + pdf-lib
👍 Pros
表示と操作で役割分担でき、それぞれの強みを活かせる
「pdf-lib」により、テキストや画像の座標位置・スタイルを詳細に制御可能
無料・オープンソース

👎 Cons
**座標系の不一致**:

- react-pdf: Yoga レイアウトエンジン（Flexbox 風）でレンダリング
- pdf-lib: PDF の座標系（左下原点、ポイント単位）で配置
- プレビューと PDF 出力で異なるレンダリングエンジンを使用するため、位置ずれが発生
  **複雑な座標変換**:
- 96dpi (794px) ⇔ 72dpi (595pt) の変換が必要
- react-pdf の計算結果を pdf-lib 用に手動で変換
- フォントサイズ、行間、文字幅の微妙な差異を吸収する必要
  2 つの API を習得する必要があり学習コストが高い
  Option B: 商用 SDK (例: PDFTron)
  👍 Pros
  プレビュー・編集機能が統合済み
  高度な機能（注釈、複数ページ操作、Undo/Redo）が標準搭載
  ブラウザ互換性や最適化がベンダー保証

👎 Cons
商用ライセンス費用が高い
一般的な利用規模では 年間 2 万〜3 万ドル（≒300〜450 万円） が目安。
ベンダーロックインのリスク（SDK API に依存）
カスタマイズの自由度は OSS より低い

Option C: iframe
👍 Pros
実装が最もシンプル
ブラウザ標準 PDF ビューアを利用でき安定性が高い

👎 Cons
編集機能やインタラクティブ性がほぼゼロ
そもそも要件を満たせない
アプリケーションとの連携も難しい
Option D: Canvas 直接操作 + jsPDF
👍 Pros
完全な制御が可能（ピクセルレベル）
軽量で外部依存を最小化できる

👎 Cons
開発工数が非常に高い
テキスト折り返し、フォント管理、イベント処理を自前実装
メンテナンスコストが大きい

Option E: DOM + Puppeteer
👍 Pros
フロント側では DOM と CSS で直感的に編集・プレビュー
サーバーサイドでは Puppeteer で ブラウザと同等の PDF 出力
React/HTML/CSS で一元管理でき、学習コストが低い
高度なレイアウトや日本語フォントも自然に処理可能

👎 Cons
サーバーサイド依存のため、リアルタイム出力には不向き
Puppeteer のセットアップと運用コストが必要
同時リクエスト数が多い場合はスケーリング課題

Discussion
技術面接での議論事項を記載

Decision
**Option E: DOM + Puppeteer を採用**

当初は Option A (react-pdf + pdf-lib) で実装していたが、以下の課題が顕在化：

- プレビューと PDF 出力の座標系のずれ（WYSIWYG の欠如）
- 3 つの PDF 生成方法（react-pdf、pdf-lib、Puppeteer）の並存による複雑性
- 座標変換ロジックの保守コストの高さ

これらを解決するため、HTML + Puppeteer アーキテクチャに全面移行した。

## 移行による成果

| カテゴリ     | 項目         | 移行前 (react-pdf + pdf-lib)                  | 移行後 (HTML + Puppeteer)      | 効果          |
| ------------ | ------------ | --------------------------------------------- | ------------------------------ | ------------- |
| **コード量** | 総行数       | -                                             | 約 650 行削除                  | -650 行       |
|              | 依存関係     | `@react-pdf/renderer`, `pdf-lib`, `puppeteer` | `puppeteer` のみ               | -2 パッケージ |
|              | PDF 生成方法 | 3 つ (react-pdf, pdf-lib, Puppeteer)          | 1 つ (Puppeteer)               | -2 方式       |
| **品質**     | WYSIWYG      | プレビューと PDF 出力でずれあり               | 完全一致                       | ✅ 向上       |
|              | 座標系       | 複数の座標系と変換ロジック                    | 単一座標系 (96dpi, 794×1123px) | ✅ 簡素化     |
|              | 情報源       | React + PDF 構文 + 座標変換                   | HTML/CSS のみ                  | ✅ 統一       |
| **保守性**   | 学習コスト   | 2 つのライブラリ API 習得必要                 | HTML/CSS (標準 Web 技術)       | ✅ 低減       |
|              | バグリスク   | 座標変換エラーの温床                          | 座標変換ロジック不要           | ✅ 削減       |
|              | テスト容易性 | PDF 生成後の検証が必要                        | DOM ベースでテスト可能         | ✅ 向上       |
| **開発効率** | デバッグ     | PDF 出力して確認                              | ブラウザ DevTools で即座に確認 | ✅ 向上       |
|              | 拡張性       | カスタムロジック必要                          | CSS Grid/Flexbox 等活用可      | ✅ 向上       |

Consequences

### ポジティブな影響

- **開発速度の向上**: HTML/CSS の知識だけで編集機能を実装可能
- **デバッグの容易性**: ブラウザの DevTools で直接プレビューを検証可能
- **バグの削減**: 座標変換エラーの撲滅により、レイアウトずれの問題が解消
- **拡張性**: CSS Grid や Flexbox など、モダンなレイアウト技術を直接活用可能

### ネガティブな影響・トレードオフ

- **サーバー依存**: PDF 生成がバックエンドに依存（ただし、元々 PDF 出力はサーバー側で実行）
- **Puppeteer のリソース消費**: Chrome/Chromium のヘッドレスインスタンスが必要
  - 対策: Docker 環境での最適化、リクエストキューイング
- **初回レンダリングの遅延**: Puppeteer 起動時のオーバーヘッド
  - 対策: インスタンスプーリング、キャッシュ戦略
- **セットアップコスト**: Puppeteer 本体 + Chromium で約 300MB
  - **緩和策 ①**: `puppeteer-core` + 既存 Chrome を利用（依存サイズを約 90%削減）
  - **緩和策 ②**: Docker マルチステージビルドで Chromium をキャッシュ
  - **緩和策 ③**: CI 環境では `mcr.microsoft.com/playwright` など最適化済みイメージを使用
  - **緩和策 ④**: Vercel/AWS Lambda 等では、レイヤー機能で Chromium を共有

### ブラウザ互換性

`react-pdf`を削除したことで、Safari 13 以前の`FinalizationRegistry`未対応問題は解消された。
現在の HTML + Puppeteer アーキテクチャは、モダンブラウザ全般で安定動作する。

### 今後の展望

- PDF 編集機能の拡張（ドラッグ＆ドロップ、リサイズ）が HTML/CSS ベースで容易に実装可能
- レスポンシブ対応やダークモード対応も標準的な Web 技術で実現可能
- 将来的な PDF 標準（PDF/A、PDF/UA）への対応も、Puppeteer のアップデートで追従可能
