# ADR-001: GraphQL通信のためのApollo採用

## ステータス

承認済み

## コンテキスト

このアプリケーションは、ReactクライアントとGraphQLサーバー間の通信を管理するための堅牢な方法を必要とします。これには、データの取得（クエリ）、データの送信（ミューテーション）、キャッシング、およびローカルの状態管理が含まれます。既存のReactおよびサーバーサイドのスタックとうまく統合できる包括的なソリューションが必要です。

## 決定

GraphQL実装のためにApolloプラットフォームを使用します。

*   **フロントエンド:** **Apollo Client**
*   **バックエンド:** **Apollo Server**

## 結果

### ポジティブな側面

*   **豊富な機能セット:** ネットワークリクエストを削減するインテリジェントなキャッシュ、ローカル状態管理、Reactフック（`useQuery`, `useMutation`）による宣言的なデータ取得など、強力な機能が標準で提供されます。
*   **強力なエコシステムとコミュニティ:** 業界標準として、優れたドキュメント、大規模なコミュニティ、そして強力なツール（Apollo Studio, ブラウザ開発ツール）のサポートがあります。
*   **シームレスな統合:** Apollo Serverは既存のサーバーフレームワークとスムーズに統合でき、Apollo ClientはReactで完璧に動作するように設計されています。
*   **スケーラビリティ:** 堅牢なキャッシュと状態管理機能は、アプリケーションの将来的な成長と複雑さの増大に適しています。

### ネガティブな側面

*   **バンドルサイズ:** Apollo Clientは、よりミニマルな代替案よりもライブラリサイズが大きくなる可能性があり、初期読み込み時間に影響を与える可能性があります。
*   **複雑さ:** 非常に単純なアプリケーションの場合、Apolloの機能セットは過剰であり、不要な複雑さを導入する可能性があります。しかし、このアプリケーションのインタラクティブな性質は、その高度な機能を必要とすることを正当化します。

## 検討された代替案

*   **`urql`:** より軽量で拡張性の高いGraphQLクライアント。強力な候補ですが、Apolloと比較してコミュニティとエコシステムが小さいです。
*   **`react-query` + `graphql-request`:** よりミニマルなアプローチ。`react-query`はサーバー状態の管理に優れていますが、この組み合わせでは、Apollo Clientが自動的に処理する正規化キャッシュなどを手動で設定する必要があります。
*   **カスタム`fetch`実装:** 最大限の制御と最小のバンドルサイズを提供しますが、キャッシュ、状態管理、React統合をゼロから構築する必要があり、時間がかかりエラーも発生しやすくなります。
