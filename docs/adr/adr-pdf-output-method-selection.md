# ADR: PDF出力方式の選定

## Context

### 意思決定の背景、及び目的

本アプリケーションでは、ユーザーが作成した請求書レイアウトを最終的にPDFファイルとして出力する必要があります。これを実現するための要件は以下です。

- エディタ/プレビュー画面と同じ見た目のPDFを生成できること（WYSIWYG）
- 日本語フォント（BIZ UDPGothic等）を正しく埋め込めること
- 高品質な印刷物として使用できる品質を保証すること
- サーバーサイド・クライアントサイドでの実行可否
- スケーラビリティとメンテナンス性を考慮すること

**注記**: レイアウトエディタとプレビュー表示方式の選定は`adr-editor-preview-selection.md`で扱う。このADRではPDF出力方式のみを扱う。

## Considered Options

以下の4つの選択肢を検討した：

- **Option A**: Puppeteer（サーバーサイド）
- **Option B**: pdf-lib（クライアントサイド）
- **Option C**: jsPDF（クライアントサイド）
- **Option D**: @react-pdf/renderer（クライアントサイド）

## Option A: Puppeteer（サーバーサイド）

### アーキテクチャ

```
クライアント（HTML/CSS プレビュー）
  ↓ GraphQL経由でHTML送信
サーバー（Node.js + Puppeteer）
  ↓ Chromiumでレンダリング
PDF出力（Base64エンコード）
  ↓ クライアントに返却
ブラウザで表示 or ダウンロード
```

**実装概要**:
1. クライアントでプレビュー表示中のHTMLを生成
2. GraphQL MutationでサーバーにHTML送信
3. PuppeteerがChromiumでHTMLをレンダリング
4. PDF生成してBase64でクライアントに返却

### 👍 Pros

- **完全WYSIWYG**: プレビュー画面と同じChromiumエンジンでレンダリング
- **HTML/CSS完全対応**: すべてのCSS機能（Grid、Flexbox、カスタムフォント等）が利用可能
- **日本語フォント自動対応**: システムフォントをそのまま使用可能
- **学習コスト低い**: HTML/CSSの知識だけで実装可能
- **開発工数が短い**: HTMLからPDF生成まで1週間程度
- **高品質出力**: ブラウザの印刷機能と同等の高品質なPDF生成

### 👎 Cons

- **サーバー依存**: PDF生成にサーバーリソースが必要
- **レイテンシ**: ネットワーク + レンダリング時間（1-3秒程度）
- **依存サイズ**: Chromiumバイナリで約170MB、puppeteer本体で約20MB
  - **緩和策**:
    - ① `puppeteer-core` + 既存Chrome利用で依存サイズを約90%削減
    - ② Dockerマルチステージビルドでレイヤーキャッシュ最適化
    - ③ AWS Lambda/Vercel等ではレイヤー機能でChromiumを共有
- **スケーラビリティ**: 同時リクエスト数に応じたサーバーリソース調整が必要
  - **緩和策**:
    - ① インスタンスプーリングで起動オーバーヘッド削減
    - ② リクエストキューイングで並列数制御
    - ③ ステートレス設計でスケールアウト可能

## Option B: pdf-lib（クライアントサイド）

### アーキテクチャ

```
InvoiceData（レイアウトデータ）
  ↓ 座標変換（px → pt、左上→左下）
pdf-lib API（drawText, drawImage等）
  ↓ PDFバイナリ生成
クライアントでダウンロード
```

**実装概要**:
1. レイアウトデータをpdf-libのAPIに変換
2. 座標系を変換（ピクセル→ポイント、原点位置変換）
3. 日本語フォントを手動で埋め込み
4. PDFバイナリを生成してダウンロード

### 👍 Pros

- **クライアント完結**: サーバー不要
- **軽量**: 約500KBの依存サイズ
- **即座に生成**: ネットワーク遅延なし

### 👎 Cons

- **座標変換が複雑**: ブラウザDOM（px、左上原点）とPDF座標系（pt、左下原点）の変換ロジックが必要
- **WYSIWYG困難**: プレビューと出力で異なるレンダリングエンジン
- **日本語フォント対応が煩雑**: フォントファイルを手動で埋め込む必要
- **テキスト折り返しを手動実装**: pdf-libは自動折り返し機能なし
- **学習コスト高い**: PDF座標系とAPIの習得が必要
- **開発工数大**: 3-4ヶ月の実装期間

## Option C: jsPDF（クライアントサイド）

### 👍 Pros

- **クライアント完結**: サーバー不要
- **軽量**: 約200KBの依存サイズ
- **実績豊富**: 広く使用されているライブラリ

### 👎 Cons

- **Canvas APIベース**: テキストレンダリングがブラウザと異なる
- **WYSIWYG困難**: プレビューと出力で見た目が異なる可能性
- **日本語フォント対応が煩雑**: フォントファイルを手動で埋め込む必要
- **複雑なレイアウト実装が困難**: Grid、Flexbox等は使えない
- **学習コスト高い**: Canvas APIと独自APIの習得が必要

## Option D: @react-pdf/renderer（クライアントサイド）

### アーキテクチャ

```
React コンポーネント（JSX + 独自スタイル構文）
  ↓ Yogaレイアウトエンジン
PDFバイナリ生成
  ↓ クライアントでダウンロード
```

**実装概要**:
1. React コンポーネントでPDF構造を定義
2. Yogaレイアウトエンジン（Flexbox風）でレイアウト計算
3. PDFバイナリを生成してダウンロード

### 👍 Pros

- **React統合**: JSXでPDF構造を記述可能
- **クライアント完結**: サーバー不要
- **Flexboxライク**: レイアウトが直感的

### 👎 Cons

- **独自レンダリング**: YogaエンジンとChromiumで異なるレンダリング結果
- **WYSIWYG困難**: プレビューと出力で座標ずれが発生
- **日本語フォント対応が煩雑**: フォントファイルを手動で埋め込む必要
- **CSS制限**: 通常のCSSとは異なる独自スタイル構文
- **学習コスト中程度**: React-PDF独自APIの習得が必要

## Discussion

### WYSIWYG（What You See Is What You Get）の重要性

請求書PDFは法的文書であり、プレビュー画面と出力PDFの見た目が完全一致することが非常に重要。座標ずれやフォントの違いは、ビジネス文書として致命的。

**各オプションのWYSIWYG精度**:
- **Option A（Puppeteer）**: ◎ プレビューと出力が同じChromiumエンジンのため完全一致
- **Option B（pdf-lib）**: △ 異なる座標系・レンダリングエンジンのため手動調整が必要
- **Option C（jsPDF）**: △ Canvas APIとブラウザレンダリングで差異あり
- **Option D（react-pdf）**: △ YogaエンジンとChromiumで微妙な座標ずれ

### 日本語フォント対応の複雑さ

**Option A（Puppeteer）の場合**:
```html
<!-- システムフォントをそのまま使用 -->
<style>
  body { font-family: "BIZ UDPGothic", "Hiragino Sans", sans-serif; }
</style>
```

**Option B, C, Dの場合**:
```javascript
// フォントファイルを手動で読み込み、埋め込む必要あり
const fontBytes = await fetch('/fonts/BIZUDPGothic.ttf').then(res => res.arrayBuffer());
pdfDoc.embedFont(fontBytes); // 複雑な実装
```

### サーバー依存のトレードオフ

**Option Aのサーバー依存は以下の理由で許容可能**:
1. **リアルタイム性不要**: PDF出力は「保存」や「ダウンロード」のタイミングで実行されるため、1-3秒のレイテンシは許容範囲
2. **プレビューは高速**: HTML/CSSプレビューは即座に表示され、編集中のUXに影響なし
3. **スケーラビリティ**: ステートレス設計でスケールアウト可能、Lambda/Cloud Runで自動スケーリング
4. **コスト効率**: 開発工数削減（3-4ヶ月 → 1週間）により、サーバーコストを大きく上回るROI

## Decision

**Option A: Puppeteer（サーバーサイド）を採用**

### 採用理由

1. **WYSIWYG保証**: プレビューとPDF出力が同じChromiumエンジンを使用し、完全一致
2. **開発生産性**: HTML/CSSの知識だけで実装可能、学習コスト不要
3. **日本語フォント自動対応**: システムフォントを手動埋め込みなしで使用可能
4. **高品質出力**: ブラウザの印刷機能と同等の品質
5. **実装コスト**: 1週間で実装可能、他の選択肢は3-4ヶ月必要

### 技術選定の決め手

| 評価項目              | 重要度 | Puppeteer | pdf-lib | jsPDF | react-pdf |
| --------------------- | ------ | --------- | ------- | ----- | --------- |
| **WYSIWYG精度**       | ◎      | ◎         | △       | △     | △         |
| **日本語フォント**    | ◎      | ◎         | △       | △     | △         |
| **開発工数**          | ◎      | ◎         | ×       | ×     | △         |
| **保守性**            | ◯      | ◎         | △       | △     | ◯         |
| **クライアント完結**  | △      | ×         | ◎       | ◎     | ◎         |

## Consequences

### ポジティブな影響

- **完全WYSIWYG**: プレビュー画面とPDF出力が完全一致し、座標ずれの問題が発生しない
- **開発速度**: HTML/CSSでPDF生成できるため、特別な学習不要で1週間で実装完了
- **高品質**: Chromiumの印刷機能を使用し、商用利用可能な高品質PDF生成
- **日本語対応**: システムフォントを自動で埋め込み、手動実装不要
- **拡張性**: CSS Grid、Flexbox等のモダンなレイアウト技術をそのまま活用可能

### ネガティブな影響・トレードオフ

#### 1. サーバー依存

**課題**:
- PDF生成にサーバーリソースが必要
- ネットワーク遅延（1-3秒程度）

**緩和策**:
- ✅ リアルタイム性不要（保存・ダウンロード時のみ実行）
- ✅ プレビューは即座にHTML/CSSで表示
- ✅ ステートレス設計でスケールアウト可能

#### 2. 依存サイズ

**課題**:
- Chromiumバイナリで約170MB
- puppeteer本体で約20MB
- 合計約190MB（圧縮後）

**緩和策**:
- ✅ **puppeteer-core + 既存Chrome**: 依存サイズを約90%削減（約20MBのみ）
- ✅ **Dockerマルチステージビルド**: Chromiumをビルドキャッシュで共有
- ✅ **AWS Lambda/Vercel**: レイヤー機能でChromiumバイナリを共有
- ✅ **最適化済みイメージ**: `mcr.microsoft.com/playwright`等を使用

#### 3. スケーラビリティ

**課題**:
- 同時リクエスト数が多い場合のサーバーリソース消費

**緩和策**:
- ✅ **インスタンスプーリング**: Puppeteerインスタンスを再利用し起動オーバーヘッド削減
- ✅ **リクエストキューイング**: 並列数を制御し、過負荷を防止
- ✅ **ステートレス設計**: 水平スケーリング可能
- ✅ **キャッシュ戦略**: 同じHTMLから生成されるPDFをキャッシュ（将来的に実装）

#### 4. ブラウザ互換性

**Puppeteerの特性**:
- ChromiumベースのためChrome/Edgeと完全互換
- Safari、Firefoxとは若干の差異がある可能性（フォント、余白等）

**対策**:
- ✅ Chromiumの標準レンダリングエンジンを使用するため、ほとんどのブラウザで同じ結果
- ✅ プレビュー画面で事前に確認可能
- ✅ 商用利用に十分な品質を保証

### 運用面での考慮事項

#### セキュリティ

- **HTMLインジェクション対策**: ユーザー入力をサニタイズ
- **リソース制限**: タイムアウト設定（30秒）でDoS攻撃を防止
- **サンドボックス実行**: Puppeteerはサンドボックス環境で実行

#### モニタリング

- **生成時間計測**: レスポンスタイム監視
- **エラーハンドリング**: 失敗時のリトライとログ記録
- **リソース使用率**: CPU・メモリ監視

### 今後の展望

- **キャッシュ機能**: 同じレイアウトのPDFを再利用
- **バッチ処理**: 複数請求書の一括PDF生成
- **カスタムフォント**: ユーザー独自フォントのアップロード対応
- **PDF/A対応**: 長期保存用PDF規格への対応
